# 通知链路 P1 修复说明

## 本轮规则

普通 HTTP 429 限流提示固定为：`请求过于频繁，请稍后再试`。

`classifyAgentError(message, failure)` 同时接收消息与结构化错误；明确429先复用既有严格额度分类器。429本身、普通限流措辞或模糊quota字段不证明耗尽；明确的insufficient_quota等错误仍由独立额度通知接管。其余旧分类行为不在本轮扩展范围。

已覆盖429状态前缀、Error/APIError、status code标记、Provider标签，以及错误message中的受限JSON对象/数组包装。只从status/statusCode及error/cause/message提取状态，限制递归深度和JSON长度；不把request_id里的429当HTTP状态，也不读取request/body中的伪造状态。

## 重试冷却

- `retry-observer.js` 只负责529/503阶段判定、历史过滤和同一重试链内去重，不再在生成通知时开始跨回合冷却。
- 桥接发送层保留唯一的QQ会话+stage五分钟门控。
- 冷却提交在最终guard和固定消息构造完成后、网关调用前。公共sendChain串行执行检查与调用，中间没有await。
- 暂停、静默、会话或回合替换、epoch变化等发送前取消不消耗冷却。
- 一旦调用发送接口，发送失败、超时或结果未知均保留冷却，不自动补发。
- 第三次重试失败的“等一下，有点卡”、第五次的“请联系管理员修复”保持原有触发语义。
- 通知生成日志不等于网关确认成功，更不等于用户已读。

## 验证

新增 `scripts/test-notice-p1-integration.mjs`，使用真实bridge源码的隔离VM和假QQ/DSH，已登记quick与full。

覆盖普通429、无429消息文本的结构化状态、明确额度429、第三/第五阶段取消、初始静默、实际发送冷却起点、五分钟边界、同阶段并发、拒绝及真实超时控制流。超时用例只在内存副本把15秒缩至40毫秒；生产超时不变。测试不替换冷却策略实现。

修复前已确认普通429与取消后新通知断言失败。模拟测试通过不表示已制造真实限流、529/503或完成QQ客户端故障验收。

## 继续取证的边界

无seq完整生命周期重放、请求级token quota措辞误判、恢复语义和身份维度仍作为独立问题。本轮不改额度三个模块、故障预算、真实状态文件，不引入熔断、状态迁移或统一通知大模块。

现有发送超时只停止等待，不保证撤销底层请求，通知可能晚到。状态原子替换不等于多进程事务或断电持久性。单实例锁、端口保护和fail-closed日志已存在；不应将它们描述为缺失，也不据此宣称所有竞态已排除。

普通429仍沿用legacy通用错误通知的五分钟门控；本轮“最终guard后提交冷却”的变更仅针对529/503阶段通知。另在隔离输入中复现：retry4已调度但未started、第三阶段通知仍排队时收到turn/error，提示可能因回合结束被取消。HEAD旧版本与当前版本表现一致，真实DSH产生该时序的条件尚需核实，本轮未调整阶段生命周期。

部署需要重启桥接加载修改。本轮实施过程不重启、不推送、不主动发送真实QQ测试消息。
