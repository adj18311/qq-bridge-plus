# 安装与使用

本文以 Windows 为例。DSH、SnowLuma 和 QQ 需自行安装并遵守各自的使用规则；本项目不提供它们的安装包。

## 1. 准备环境

1. 安装 Node.js 22.13.0 或更高版本，在 PowerShell 中运行 `node --version` 和 `npm --version` 确认可用。
2. 安装并启动 DSH Desktop，配置可用的模型和凭据。默认地址为 `http://127.0.0.1:3080`；如使用其他地址，以实际配置为准。
3. 安装并启动 SnowLuma，按其引导登录 QQ、完成接入。启用 OneBot HTTP 服务端和 WebSocket 服务端，记下实际监听地址、端口和可选的 access token。
4. 获取本项目代码，进入项目目录。请使用可信来源，不要把别人提供的配置文件或 Cookie 当作自己的凭据。

默认 HTTP 和 WebSocket 端口分别是 3000、3001；如果端口不可用，在 SnowLuma 中改为可用端口，并在桥接配置里填写对应地址。两个服务端口不要混填。

## 2. 安装依赖并创建配置

在项目目录打开 PowerShell：

```powershell
npm ci
Copy-Item config.example.json config.json
```

第二条用于首次安装；如果已经有自己的 `config.json`，不要覆盖，先备份并按需要手动合并新配置。`npm ci` 需要网络，并会运行项目的 `postinstall` 脚本修补本机依赖副本。

用文本编辑器打开 `config.json`，重点检查：

- `dsh.baseUrl`：DSH 的实际地址；`provider`、`model` 和 `reasoningEffort` 与 DSH 中可用的模型配置一致。
- `snowluma.wsUrl` / `snowluma.httpUrl`：分别填写 SnowLuma OneBot 的 WebSocket 和 HTTP 地址；配置了 access token 时填写 `snowluma.accessToken`。
- `ownerQQ`：管理员 QQ 号。
- `allow.private` / `allow.groups`：按需要填写允许使用的私聊用户和群；默认空数组且 `allowAllWhenEmpty` 为 `false`，因此默认不响应任何会话。
- `consolePort`：本地控制台端口，模板默认 3100；与其他程序冲突时更换。

不要将真实配置上传到 GitHub，也不要将 DSH 凭据、Cookie 或控制台令牌发给他人。建议先只允许自己的私聊，确认正常后再逐步放开群聊。

## 3. 安装 DSH 侧组件

在项目目录运行：

```powershell
node scripts/setup-dsh.mjs
```

该脚本会安装聊天预设、注册本项目插件并配置 MCP；默认操作 DSH 的 `web` profile。检测到适用的 DSH 0.2.1 版本时，还会部署对应的 Team 适配片段。它会修改本机 DSH 配置及插件链接；已有 DSH 环境建议事先备份 profile 和配置，并核对脚本输出。DSH 0.20 不在支持范围内：0.2.1 的改动之后没有重新跑 0.20 的回归，装了也可能不起作用，详见 docs/COMPATIBILITY.md。

**完成后重启 DSH Desktop。** 如果脚本报告找不到 DSH CLI 或安装失败，先处理输出中的错误；不要将跳过或失败当作安装成功。安装路径改动、切换到另一份项目副本时，也要重新检查 DSH 插件链接指向哪份代码。

## 4. 启动并验证

1. 确认 DSH 和 SnowLuma 已启动，QQ 账号在线，OneBot 端点正在监听。
2. 在项目目录运行 `npm start`；Windows 也可用 `start.bat` 启动守护模式。守护窗口关闭后不再由它拉起桥接；同一套配置不要同时运行多个桥接实例。
3. 打开 `http://127.0.0.1:3100`（如改过端口，以配置为准），按启动提示使用控制台令牌登录。令牌属于敏感信息。
4. 在白名单内的 QQ 私聊发消息，确认收到回复；再按需测试群聊。使用二代仿真功能时，在控制台选择对应的 `reserved2` 模式，并确认相应工具已启用。

人格卡位于 `roles/`，可在控制台按需选择。`role.maxInjectChars` 控制注入字符上限；模板值是 10000，实际运行以自己的配置为准。

## 5. 贴吧功能：安装、配置和使用

贴吧功能已经包含在项目代码和 DSH 预设中，不需要另外安装贴吧插件。它用于**查看吧页和读取帖子**，不会替你发帖或回复。需要桥接、DSH 侧预设/MCP 和二代仿真会话正常工作。

### 5.1 启用工具

先完成第 2、3 节，并重启 DSH。在控制台的二代仿真工具设置中检查 `qq_tieba_list`、`qq_tieba_read`；也可以在现有 `config.json` 的 `socialV2.tools` 对象中加入以下字段：

```json
"tiebaList": true,
"tiebaRead": true
```

这两行是现有 `tools` 对象的成员，不是独立完整 JSON 文件；注意与相邻字段之间的逗号。不要为了添加它们删掉已有的工具配置。这两个字段未写入模板时按启用处理，只有明确设为 `false` 才关闭。修改配置文件后重启桥接；如果预设或 MCP 安装有变化，重新执行安装脚本并重启 DSH。

### 5.2 可选：配置自己的登录态

不配置 Cookie 也可以尝试读取公开内容，但可能遇到限制、验证或内容不完整。需要登录态时，使用自己账号、自己有权访问的 Cookie，步骤如下：

1. 在浏览器登录百度贴吧。打开开发者工具的网络面板，刷新贴吧页面，找到发往贴吧域名的请求，在请求头中找到 `Cookie`。不同浏览器界面可能不同。
2. 在**项目目录之外**创建一个仅自己可读的 UTF-8 文本文件，例如 `D:/qq-bridge-secrets/tieba.txt`。将该请求头的 Cookie **值**放在文件第一行，格式为 `字段名=值; 另一个字段名=值`；不要写 `Cookie:` 标题，不要换行，也不要附上其他请求头。
3. 在现有 `config.json` 的 `socialV2` 对象中加入或修改下面的对象；如果已有 `tieba`，只修改其中的 `cookieFile`，不要创建重复的 `socialV2`：

   ```json
   "tieba": {
     "cookieFile": "D:/qq-bridge-secrets/tieba.txt"
   }
   ```

4. 保存后重启桥接。路径必须指向实际文件；示例路径可自行更换。Cookie 留在单独文件中，配置里只写路径。

Cookie 相当于登录凭据：不要上传仓库、粘贴到 QQ、提交 Issue、放入发布包或发给他人。泄露时应尽快退出相关登录会话并更新凭据。文件能被读取不代表登录态一定有效；过期、权限不足和平台验证仍可能导致读取失败。

### 5.3 在 QQ 中使用

在已授权且使用二代仿真的会话里，可以直接说：“看看某某吧最近有什么帖子”或“读一下这个贴吧帖子”，并提供帖子链接。模型可使用 `qq_tieba_list` 查看吧页，用 `qq_tieba_read` 根据帖子链接中的数字 ID 读取内容；需要后续页面时，可明确说明要读哪些页。一次最多读取 10 页；图片一次最多 10 张，单张最多 4 MiB、合计最多 25 MiB，超出的部分会注明。模型能否理解图片，还取决于模型的图片输入能力和图片是否可获取。

自主浏览由会话机会和模型决定，并非定时任务。默认自主访问每天最多 12 次、单次读帖最多前两页，01:00–08:00 不自主访问；这些限制可以通过 `socialV2.patrol` 调整。若只希望响应明确请求，可将 `socialV2.tools.patrol` 或 `socialV2.patrol.enabled` 设为 `false`；这不等于关闭两个贴吧读取工具。

用户明确要求的读取不计入自主访问预算，但仍受抓取节流约束。吧页和帖页分别限速：相邻请求至少间隔 3 秒，各自每分钟最多 6 次；遇到安全验证后有冷却期。被拦时应等待或按提示使用搜索结果，不要反复请求或尝试绕过验证。搜索降级结果不保证完整或实时。

### 5.4 排查

- **找不到工具**：确认使用 `reserved2`、两个工具已启用，DSH 安装脚本成功执行且 DSH 已重启。
- **工具被拒绝**：检查会话白名单、工具开关及自主访问限制；用户请求和自主访问的限制不同。
- **登录或内容异常**：检查路径、文件权限、单行格式及 Cookie 是否过期；不要把 Cookie 内容写进日志或求助帖。
- **提示安全验证或冷却**：停止重复请求，等待冷却或使用提示的搜索降级；这不等于帖子不存在。
- **看不到图片**：检查图片是否仍可访问、模型是否支持图片输入，以及单次读取的图片和大小限制。

## 6. 升级与备份

从已有版本迁移前，先停止相关桥接并备份配置、`state/` 和 DSH profile；不要上传这些数据。完整说明见[升级说明](UPGRADE.md)。迁移后先检查插件链接和白名单，再做真实 QQ 收发测试。

## 7. Windows DSH Desktop 随机端口自动发现

DSH Desktop 重启后可能改用随机本地端口。Windows 上桥接会尝试自动发现当前实例的端口：先按进程归属找到 DSH Desktop 的监听端口，再通过 DSH 鉴权并核验 qq-mode 命名空间（qq-mode 是鉴权后 `settings` 返回的命名空间核验，不是独立鉴权机制），通过后才把进程内连接切到新地址；不会自动修改 `config.json`，显式配置始终保持原样。

排查时先看日志：

- 自动发现日志统一带 `[dsh-discovery]` 前缀，包含阶段、原因和耗时。
- 每轮发现都有时间预算，未成功时持续重试，且重试之间不重叠。
- 只有验证通过的候选端口才会被采用；验证不通过时保留原连接并继续重试。

以下情况仍需要手动检查，自动发现不保证成功：

- DSH 没有启动，或桥接与 DSH 不在同一台机器、同一用户会话下。
- 没有安装或没有启用本项目配套的 QQ 插件。
- 多个 DSH 安装或实例共享同一个 `DSH_HOME`：仅凭进程名与命名空间无法唯一确定目标实例，选择存在歧义。
- DSH 使用了非本机回环地址、代理或自定义鉴权配置。

自动发现以 Windows DSH Desktop 为主要覆盖场景，其它平台与非 Desktop 版 DSH 未逐一验证，仍以 `dsh.baseUrl` 为准；也不承诺消息处理不受阻塞或固定恢复时限，恢复取决于 DSH 重启与实际重试节奏。需要固定地址时，不只改 `dsh.baseUrl`：同时把 `dsh.autoDiscoverDesktop` 设为 `false` 并重启桥接，避免发现失败后仍跟随其它实例；该开关只禁止桥接自动切换，并不会让 DSH 本身使用固定端口。共享 `DSH_HOME` 的多实例无法可靠自动识别目标，建议按上述方式关闭自动发现并手动指定地址。
